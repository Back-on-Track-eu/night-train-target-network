<ReportCard kicker="05 · From a crowd of proposals to one network" :big="n(d.funnel.typical)" title="of your proposals are typical night trains">

Assuming a typical night train, one way, covers **{{ n(env.km[0]) }}–{{ n(env.km[1]) }} km**, takes **{{ env.h[0] }}–{{ env.h[1] }} hours** and averages **at least {{ env.min_speed_kmh }} km/h** — the yardstick of our [general position paper](https://back-on-track.eu/back-on-track-europes-general-position-paper/) as the gallery's _typical night trains_ filter applies it — {{ pct(d.funnel.typical_share) }} of your proposals qualify. Of the rest, {{ n(d.funnel.too_short) }} are shorter than {{ n(env.km[0]) }} km, {{ n(d.funnel.too_long) }} longer than {{ n(env.km[1]) }} km, {{ n(d.funnel.over_time) }} would take more than {{ env.h[1] }} hours one way, {{ n(d.funnel.under_time) }} fewer than {{ env.h[0] }}, and {{ n(d.funnel.too_slow) }} crawl below {{ env.min_speed_kmh }} km/h — overlaps included.

This is a first sieve, not a verdict on anyone's route. Between here and a study we can hand to the EU, every proposal goes through filtering — duplicates, tests, the envelope — and refinement with the people who know the line. The cards that follow use only the {{ n(d.funnel.typical) }} typical night trains.

Many of them are the same train drawn twice: the {{ n(d.funnel.typical) }} boil down to **{{ n(d.funnel.pairs) }} distinct city pairs** (termini within {{ env.city_km }} km count as one city), and grouping routes that share most of their stops leaves **about {{ n(d.funnel.corridors) }} corridors** — each with one to {{ n(d.funnel.max_variants) }} variants to refine.

Our position paper puts the number Europe needs at about 300 — so are we nearly done after two weeks? No. These {{ n(d.funnel.corridors) }} come out of a first sieve run on a first-generation model. The real demand model, the refined cost model and the routing fixes that are coming (see the [September product update](/updates/2026-09)) will all tighten the mesh, and a fair share of today's corridors will not survive that reality check. So keep drawing — above all where the map above is still dark.

<ReportCard kicker="07 · What it would take to run them" :big="compact(d.supply.train_km, 0)" title="train-kilometres a year">

Added up, the {{ n(d.funnel.typical) }} typical night trains come to {{ n(d.supply.departures) }} departures a year and {{ compact(d.supply.seat_km) }} seat-kilometres offered. Read these as what the model says today, not as a forecast: every proposal is counted on its own, with a first-generation supply and demand model behind it, and the model will be reshaped considerably before any of this becomes a study. Supply side only, too — the demand assumption behind the revenue figures is still the simplest one that works, so we are not summing passengers yet.

Counted route by route they would need {{ n(d.supply.trainsets) }} trainsets — a theoretical figure, because it ignores every network effect. Most of your trains run three nights a week and sit idle the other four, when the same set could serve another corridor; if every set ran every night, {{ n(d.supply.trainsets_nightly) }} would do. The real fleet question can only be answered by looking at proposals together, as one network — the network analysis mode we are planning to build, precisely because this report cannot answer it yet.

What a train-kilometre costs is calibrated — as of today: the median proposal runs at {{ n(d.supply.cost_median, 1) }} € per train-km, all costs included. We will keep pushing the cost algorithm towards real-world behaviour, component by component; the feedback button on every cost factor is how you help.
